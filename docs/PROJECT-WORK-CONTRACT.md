# Project work loop (0.9.3)

## Native execution evidence and independent verification

`execution.prepare {command}` freezes a bounded source fingerprint before a command is executed by the existing native task, at the project root and in the current native turn. `execution.read {id}` returns the preparation and captured evidence. The agent does not submit stdout or an exit code. Morrow observes the exact native command's start and terminal events and stores command, cwd, output, exit code, native item/task/turn IDs, source fingerprint and provenance in SQLite. Prepared commands bypass renderer event coalescing so fast start/end events remain observable. A missing start, unknown exit code, truncated output, directory mismatch, source change or interrupted observation cannot certify success. Old native history cannot be attached retroactively as a new execution. Captured evidence is immutable through the work interface; restarted preparations remain unknown.

Native automatic approval can label the start event `source:agent` and the completion event `source:unifiedExecStartup` for the same command. Both accept the same strictly parsed literal shell wrapper, preserving exact command/task/turn/item matching and rejecting wrappers with appended shell operations. This is event compatibility, not automatic approval by Morrow; existing unknown evidence is not rewritten after the fix.

Expectations additionally accept `source:{kind:execution,command}` with a mandatory scalar rule, typically `/exitCode equals 0`. Rules use the actual native receipt. Execution evidence requires complete output and matching source fingerprints both during capture and at assessment; stale execution cannot certify the current source. File and HTTP evidence retain their original provenance. File capture proves the bytes collected, not that a reported command ran.

New choices use `evaluationVersion:2`. Their `decision.review` with `outcome:improved` first performs the existing field/window/guardrail checks, then requests independent verification. While verification is pending, failed or unknown, the response contains `pendingVerification:true` and `verificationId`; the decision remains active and its original contract is unchanged. `feature.upsert` requesting verified/resolved similarly remains investigating until verification passes. Final optional reports cannot bypass this gate. Legacy choices with version 1 or no evaluation protocol retain their historical interpretation; old records are not retroactively certified.

`verification.request {itemId?,decisionId?,evidenceIds}` can explicitly prepare this same gate. It creates a fresh native task through the existing Codex App shared runtime, with no project-work grant, approval policy `never`, a read-only sandbox and network disabled. The main channel/task binding does not change. The reviewer gets the frozen goal/expectations and original evidence, not the implementer's proposed success conclusion. It must inspect source and relevant counterexamples independently, and return exactly one result per expectation. No successful native command, missing checks, a blocking finding, source changes, malformed output, permission requests or abnormal completion prevent a pass. A recorded file change also stops verification. These are checks on native shell execution and the work interface, not a claim of a separate security boundary around arbitrary integrations loaded by native configuration.

The reviewer has a 5-minute timeout and a 4-MiB native event journal. It runs through native tools rather than service-side arbitrary command execution. The service only runs bounded, fixed Git reads for source fingerprinting. The journal retains initial native items and subsequent field changes/text appends without repeatedly charging accumulated output against the limit. Jobs, original prompts, model/task/turn IDs, raw events, conclusions, limitations and failed attempts persist. `verification.read {id}` returns the job, current-version validity and its events; project work views show compact results with the same feature provenance.

One reviewer runs at a time per service; pending work is serialized per project and each started review consumes the channel's existing UTC daily run budget. Queued/running reviews hold new autonomous turns in that project without spending a run, including turns made due by older reassessment signals; other projects can continue. Manual run requests report the pending review. This does not interrupt a turn already in progress when it submits its review or prevent user guidance through the native conversation. Further source edits invalidate the frozen review. A completed review signals the original decision/channel, respecting manual pause. Pausing stops its review; timeouts, connection ambiguity and restart keep unknown results and persist an intent to interrupt only that exact review task/turn. No uncertain send is automatically replayed. Identical current materials reuse their prior result. After resolving an environment problem, `verification.retry {id}` allows one additional attempt per identical material set per UTC day, preserving the previous unknown result and sharing the daily budget. Failed counterexamples require changed source/evidence. A validated decision.review or feature completion request is saved in `loop_finalizations`. After a pass the service revalidates current source, latest evidence and record revision, then applies the request transactionally without another native turn. Read `context.finalizations` for applied/stale/rejected status; an old requestId still returns its original pending response. Concurrent edits are never overwritten, and failed/unknown reviews leave the target unfinished. Durable terminal receipts drain after restart without repeating a model run.

New release proposals require a current passing review for every associated feature and retain its verification IDs in the sealed review contents. Review records referenced by releases remain available beyond the recent-history limit. Publication still requires human approval of the exact sealed artifact and review hash, and uncertain publication is reconciled rather than resent.

Source fingerprints cover Git-tracked and unignored files, or bounded plain-folder traversal excluding common dependency/build/cache directories. The `source-v2` scheme excludes `node_modules` and `.pnpm-store` at every depth, including accidentally tracked dependency links, while retaining application assets and tracked build inputs. It hashes complete content and file modes, up to 5,000 files and 1 GiB, with a reusable 512-KiB buffer and a 5-second read limit. Application symlinks, submodules, special files, concurrent file changes and oversized sources fail explicitly. The scheme's distinct digest prefix invalidates older passes for current-source certification without changing historical evidence. These are before/after **source** fingerprints, not an immutable execution filesystem, dependency lock attestation, reproducible-build proof, deployed-version check or causal measurement. Independent model review can still miss errors. Existing metrics/contracts and independent feedback remain necessary; passing tests or review does not establish business uplift.

Before dispatching a decision review, the service mechanically checks that every planned source has a new observation in its original window, execution evidence binds the current source, and scalar rules are met. Late records cannot certify a closed window; missing/stale/contradictory fields are rejected before spending a reviewer run. The same constraints apply to current-proof lookup. A qualitative result still needs independent judgment. HTTP watch evidence preserves the complete response JSON, so rule pointers address its original fields rather than an invented `/value` wrapper.

New `acceptance-v2` reviews bind the project goal, current channel direction and immutable decision expectations. When structured expectations exist, feature title/progress description is context rather than acceptance criteria; standalone feature reviews continue binding the full description. A covered evidence subset reuses the latest review, including a failed result; it cannot select an older pass. New observations from planned sources are included and invalidate incomplete older reviews. Old records retain their original subject scheme and are not rewritten as successful.

Additive, idempotent tables: `loop_executions`, `loop_verifications`, `loop_verification_events`, `loop_finalizations`. Existing projects, settings, native bindings, pause states and original records are retained. The UI keeps the accepted compact shell, adds an expandable independent-review record, labels native versus file evidence, and displays the saved next direction after a decision is reviewed.

## Observation contracts and evidence-based review

New `decision.choose` calls require `expectations` (1–8 entries, including an `outcome`; a `stop` choice may use an empty list). Each entry contains `{id,kind:outcome|guardrail,claim,scope,source:{kind:file,path}|{kind:watch,watchId},verification,disconfirm,notBefore?,deadline,rule?:{pointer,operator:gte|lte|equals,expected}}`. A file may be a planned output that does not exist yet, but its canonical location must be inside the project. Watches must belong to this project and not be cancelled. Sources, conditions, rules and deadlines are frozen with the choice. `notBefore` defaults to the choice's creation time; delayed measurements must set it explicitly. Numeric comparisons require finite numbers and strict matching types. Rules operate on captured JSON, not model-reported scores.

Version 0.8 decisions carry `evaluationVersion:1` and an evidence insertion cursor. The cursor excludes pre-choice evidence even when timestamps coincide. New `decision.review` calls for these decisions require `assessment:{results:[{expectationId,verdict:met|not_met|unknown,reason,evidenceIds}],conditions:matched|changed|unknown,conditionReason,diagnosis:expected|pending|measurement|execution|assumption|environment|uncertain,explanation,adjustment:continue|observe|measurement|method|assumption|stop,understandingRefs?:[{id,revision}]}`.

Every original outcome and guardrail must be represented exactly once. Evidence must come from its frozen file or exact HTTP watch, be newly collected inside its observation window, and include the latest qualifying observation from that source. Agent-authored evidence cannot stand in for collection. Missing data, invalid field types and premature observations cannot establish a conclusive result. Rules mechanically check the captured scalar and reject a conflicting declared verdict; qualitative interpretation remains explicitly attributed to the agent. `improved` requires every outcome and guardrail to be met. `not_improved` requires an actual unmet expectation. Changed/unknown comparison conditions and pending/broken measurement permit an inconclusive review, retaining the measured values. An uncertain causal explanation does not erase an otherwise observed outcome.

Reconsidering an assumption requires saving a new or revised project understanding first and citing its current revision; referenced original assumptions must have advanced in version. The assessment, evidence references and original plan are saved transactionally in SQLite, with immutable revision history and idempotent replay. Memory search also includes expectation scope, disconfirmation and assessment explanations. These changes do not train native model weights, independently establish causality, or guarantee that the agent's chosen metrics represent all user goals.

Captured evidence from an expected source signals its dependent decisions without unpausing work. For a new HTTP expectation, one fresh sample is retained even if the watched value has not changed since the old baseline. Changes to other JSON fields explicitly referenced by expectation rules are also retained; unchanged valid samples remain quiet. Captures now retain `watchId`. Old HTTP evidence is not retroactively assigned to a watch. Expectation deadlines participate in reassessment scheduling.

Existing decisions without `evaluationVersion` retain their previous review protocol and are labelled as historical textual reviews in the UI. They are not backfilled with invented observation contracts. This increment adds JSON fields to existing tables and preserves old projects, native bindings, settings, pause states and records. The project judgment document and associated feature expose the same compact, expandable `预期与实际` record; no new configuration form is introduced.

## Project understanding and decisions

New projects start with one paused `自主推进` responsibility and a 32-run daily limit; existing channels are untouched. The native agent chooses strategy. The framework persists its basis, alternatives, expectations, review boundaries and subsequent assessments.

- `understanding.upsert`: `{id?, revision?, kind:fact|assumption|unknown|capability|constraint, title, statement, relevance, verification, status:active|invalidated|retired, evidenceIds, reviewAt}`. Facts and invalidations need evidence references, which retain their original agent/file/HTTP provenance. This does not independently certify the statement. Updates require the current revision; duplicate titles reuse the original record. Each version is saved.
- `decision.choose`: `{objectiveVersion, options:[{title,kind:act|investigate|build_capability|observe|stop,benefit,cost,uncertainty}], selected, rationale, nextStep, expectedOutcome, evaluation, stopWhen, expectations, understandingRefs:[{id,revision}], memoryRefs?:[{kind,id,revision,use:apply|adapt|avoid|not_applicable,reason}], evidenceIds, watchIds, reviewAt, maxRuns, itemId?}`. One current choice per channel; active choices cannot duplicate a feature or title across channels. A fresh goal/direction hash and current, unexpired understanding revisions are required. Original choices and goal snapshots are immutable.
- `decision.review`: `{id,revision,outcome:improved|not_improved|inconclusive|abandoned,conclusion,evidenceIds,nextDirection,assessment}`. Closes the choice, retaining its original expectation and assessment separately. New decisions follow the observation contract above; legacy decisions omit `assessment`. The overall interpretation is still an agent assessment, not a claim of independently measured business impact. Afterwards the agent can choose another action, observation or stopping point.
- `memory.search`: `{query?,kind?:understanding|decision|learning,limit?:1..30,offset?}` searches all project records with literal, space-separated terms and bounded pagination. Results retain status; invalidated/retired entries are historical lessons, not current facts.
- `memory.recall`: `{query?,itemId?,limit?:1..12}` ranks project records by local lexical relevance and association with the same feature. It searches the full current memory corpus, including retired/refuted knowledge and reviewed failed decisions, without a recent-record cutoff. Chinese bigrams and other word tokens are supported. Automatic recall uses the goal, direction, current focus and selected action; a specific query can refine it. Matches carry status, revision, source references, excerpts, cautions and matching reasons. Ranking is neither semantic understanding nor a confidence/causality score. Use `memory.read` to check full content and conditions.
- `memory.read`: `{kind,id,beforeRevision?}` returns the full scoped record and up to 20 historical understanding/decision/learning versions, with a continuation cursor. Learning mutations now save immutable snapshots; the first update of a legacy entry preserves its currently available revision before writing the new one. Earlier missing snapshots are not invented, and the existing audit trail is retained.

`memoryRefs` records the agent's actual applicability assessment, not every automatically retrieved suggestion. Up to 12 unique references retain their exact revision, a bounded historical snapshot and the reason for applying, adapting, avoiding or judging the experience inapplicable. Current project ownership and revision are checked transactionally. Active decisions cannot be cited as reviewed experience. Direct `apply` rejects invalidated/retired/refuted/stopped records, expired understanding and failed/abandoned decisions. `adapt` remains possible with an explanation and a new decision's evaluation; this permits deliberate re-experimentation without treating the old result as success. The assessment is agent-authored, not proof that retrieval caused a better outcome.

`context.strategy` includes the exact goal/direction version, daily budget, bounded previews, active choices and review reasons. Its `relatedMemory` presents up to six relevant records before the larger history sections. Long fields are marked `truncated`; `counts` and `partial` expose omitted strategy records. The outer `learning` list now contains the latest 12 bounded summaries with `learningCoverage` counts; full history stays in SQLite and is retrieved through `memory.recall/search/read`. Desktop `GET /api/projects/:id/work` retains its existing record coverage and includes the compact 当前判断 document, with expandable experience references and their original evidence.

New native guidance, relevant observation/release signals, changed or expired understanding, changed goals, review deadlines and spent attempt rounds require reassessment. Signals and run attribution survive restart. Signals received during a running turn remain available to its next context; manual pause always wins. At completion, an active choice's review time can shorten an existing wait. Observation/stopping choices wait for feedback or their review time instead of consuming an attempt budget in a polling loop. Once reassessment is due, `feature.upsert` and `release.propose` reject until the choice is reviewed; evidence collection, understanding updates and review remain available. This gate governs the Morrow work interface, not arbitrary native shell commands. Existing native permissions and the separate daily scheduler budget remain authoritative.

Revisions to cited experience also wake dependent channels and require review, except references explicitly judged `not_applicable`. An understanding reference that was current when chosen carries its review deadline into scheduling. An already-expired record deliberately cited for historical adaptation does not immediately force an endless review; it retains its caution and still requires reassessment when revised. Reference snapshots never change when their sources are updated. Existing decisions without `memoryRefs` remain readable and usable.

Additive tables: `strategy_understanding`, `strategy_decisions`, `strategy_revisions`, `strategy_runs`, `strategy_signals`. Mutations use the same expiring scope, transactional idempotency and project isolation as the existing work interface. No automatic skill registry, cross-project memory transfer, autonomous channel reorganization or general deployment adapter is claimed by this increment.

## Existing work and publication interface

`POST /api/agent` uses a private, expiring run grant distinct from the desktop credential. The grant identifies one project, channel and active run. `context` and `evidence.read` are read operations. Mutations require a stable `requestId`; the mutation and cached result commit in the same SQLite transaction. Replays return the same result, different payloads under the same ID conflict, and fresh operations after the run ends are rejected.

Operations: `feature.upsert`, `evidence.record`, `evidence.capture`, `learning.upsert`, `watch.create`, `watch.cancel`, `wait`, `release.propose`. Item and learning updates use revisions. Evidence distinguishes agent statements, actual file capture and HTTP capture. `context` abbreviates long evidence with `truncated:true`; `evidence.read` returns the preserved content.

`GET /api/projects/:id/work?itemId=...` returns shared observations, learning, watches and releases. `POST /api/releases/:id/review` accepts the desktop credential, exact `reviewHash`, `approve|reject`, and optional feedback. The agent grant cannot call this endpoint. `POST /api/releases/:id/reconcile` checks an uncertain outcome without resending publication.

Release preparation copies a project-contained artifact (up to 8 MiB) into private storage and binds its SHA-256, target, checks and review text. The HTTP adapter sends `POST {releaseId,reviewHash,artifact:{name,sha256,bytes,base64}}` with `Idempotency-Key: releaseId`. A receipt must match `releaseId` and `artifactSha256` and report `status: published|failed`. The GET status endpoint receives a `releaseId` query parameter and returns the same receipt. A lost or mismatching response stays unknown; recovery queries status rather than reposting.

HTTP JSON observations are bounded to 512 KiB with a 10-second timeout, explicit JSON Pointer, at least 30 seconds between polls and up to 50 active monitors per project. `continuous` defaults to true: after a condition is triggered or a review deadline expires, changed values still produce evidence and wake the enabled source channel. Identical values stay quiet. `continuous:false` makes an observation end after its condition/deadline. Cancellation or pausing the channel stops scheduled collection. Waits may refer to another channel's source in the same project.

`loop_grants`, `loop_calls`, `loop_evidence`, `loop_learning`, `loop_watches`, `loop_waits`, `loop_releases` are additive SQLite tables. Native executions retain their exact task/turn IDs. Scheduled turns use native automatic review and the saved workspace scope, and never steer an unexpectedly active user turn. Shared-host selection first preserves a verified launch, otherwise probes loaded task IDs without resuming candidates; ambiguous ownership fails explicitly. Local projection revisions have a fresh epoch for each shared connection, so daemon restarts cannot discard the new stream as stale.

### Unknown-review retries

An explicit retry carries the latest unchanged completion intent into the new review, preserving the original rejected intent and original run reference. Concurrent target changes or newer intents prevent carrying it. Bounded successful tool observations from the prior attempt may guide the retry; they never count as this attempt’s independent check or a passing verdict. The same-material daily retry limit and review timeout remain unchanged.
