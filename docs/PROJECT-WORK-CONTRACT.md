# Project work loop (0.9.3)

## Task charter, turn notes and compact responses

One channel keeps using one Codex App task. Its full **charter** contains the role, project name/path and goal, the full labelled user brief and revision, direction, reporting rules and authorized scope. The capability inventory is referenced through `contract.nativeCapabilities`. A **turn note** carries the brief revision, bounded focus/next-step text (not the stored work JSON), usage, board digest and `morrow-next` reminder. The unchanged direction is not repeated in notes. User brief contents are preserved and remain in the task's original charter; `contract` supplies operation rules, not a copy of that brief.

Delivery is tracked in `channel.promptCharter` (`{threadId, hash, sentAt, turnsSince}`). The full charter is sent for the first delivery, a changed thread/hash (including brief, goal, direction or permissions), or missing delivery. On the tenth turn, after an accepted but unfinished turn, or after a turn without a work decision, the prompt carries a **charter review**: bounded goal/direction, brief version, a reference to the original charter, and the release/evidence/needs_input rules. A rejected native send still clears delivery; reminders never count an unaccepted first turn as delivered. Chat and App-owned turns are ignored when looking for the previous scheduled turn. The fixture CLI prompt path is unchanged.

The board digest prioritizes human and last-touched items. Detailed rows contain `#number kind status title` and a next step of at most 150 characters; remaining items are represented by number, resolved items by count, with a `context` pointer. The board is capped at 1200 characters and can be reduced further to keep the complete note plus tool entry within 1500. The charter-review target is 2500 characters. The full charter and executable paths are never truncated. Long input fields are shortened only in the prompt, not in stored records. A grant-bearing turn omits the fallback `morrow-report` schema; without a grant that schema remains available.

Every run's existing private grant directory now also contains a mode-0600 `tool.sh`. The prompt invokes it with `sh '<absolute-run-path>/tool.sh' --operation context`. It only executes the existing Node/agent-cli command with that run's `--context` and forwards `"$@"`; it contains paths, no token. CLI operation names and input shapes are unchanged: `--operation`, `--input -` for JSON stdin or `--input <file>`, and a stable `--request-id` for writes. Retry with the same ID and content. The original direct Node CLI invocation remains supported. Project/run authorization, expiry and human-only release approval still reside in the existing service, not the wrapper. Never read or print the credential file. `scripts/prompt-size.ts` checks note/review/tool-entry budgets of 1500/2500/250 on the isolated fixture; path length affects the tool-entry length, and executable paths must not be cut to satisfy a text budget.

`contract` is a new read-only operation on the same grant, returning `{operations, releaseAdapter, principles, nativeCapabilities, briefRevision}`: exactly the static text `context` used to repeat in every response. `context` now returns data plus a short `hint` pointing at `contract`. Its `project` carries `id`, `name`, `goal` and `briefRevision` only; the brief text itself lives in the charter. Its `evidence` rows drop `data` and carry `bytes` beside the existing `id`, `itemId`, `summary`, `source`, `origin`, `digest`, `observedAt`, `watchId` and `createdAt`, so nothing is abbreviated with `truncated:true` any more and `evidence.read {id}` is the one way to replay content. `evidence.capture` and `evidence.record` return that same row rather than echoing the captured file or payload, and `feature.upsert` returns `{id, number, revision, kind, status, title, ownerChannelId}` plus `verificationId`, `pendingVerification` and `finalizationId` when a verification is involved. `decision.*`, `execution.*`, `watch.*`, `wait` and `release.propose` responses are unchanged. This is a context-cost change, not a permission or evidence change: the same records are stored, the same gates apply, and nothing is inferred about a turn actually having read what it was sent.

## Item ownership and one shared working tree

All channels of a project share one board and one project directory, so two directions can only divide work safely if each item has one responsible channel and no channel starts on another channel's uncommitted changes.

**Ownership (事项归属).** `WorkItem` carries an additive optional `ownerChannelId`. Absent means 无人负责. A channel claims an unowned item by advancing it through the work interface — `feature.upsert` creating or updating it, `decision.choose` with `itemId`, or `verification.request` with `itemId` — and the claim is audited as `item.claimed` (actor `system`, because Morrow assigns responsibility as a consequence of the write; the write itself keeps its own `feature.*`/`decision.chosen` audit). An item stored as `resolved` is released (`ownerChannelId` cleared, audited `item.released`), including when a deferred completion is applied after its review passes; a `blocked` item keeps its owner, since that channel stopped on it and owes the next step. Any of those three operations on an item owned by a *different* channel is refused with 409 `事项 #n 由频道「<name>」负责；只能推进分派给本频道或无人负责的事项`, and nothing is written. Reads (`context`, `memory.*`, `evidence.read`, `verification.read`, `observation.read`) are never restricted, and neither is contributing an observation or a lesson: `evidence.record`, `evidence.capture`, `learning.upsert` and `watch.create` may still reference another channel's item, because those add shared material rather than advance the item. The legacy `morrow-report` board path is unchanged and claims nothing. Ownership is orthogonal to the item's own `revision`: a claim or release does not bump it, so an in-flight `feature.upsert` is not invalidated by bookkeeping.

**Human assignment.** `PATCH /api/items/:id` (desktop credential) additionally accepts `ownerChannelId`: a channel of the same project, or `null` to release. A channel outside the project is 404. Reassigning an item a channel currently owns is allowed — the human decides — and is audited as `item.assigned` with actor `human` beside the usual `item.updated`. Like every other field on that route, an assignment bumps the item's revision. The desktop board rows and the item detail show the responsible channel as a small chip, and the item detail's 分派给频道 select calls this route.

**Prompt.** The board digest annotates each unresolved item with `｜本频道` when this channel is responsible, `｜负责：<频道名>` when another one is, and nothing when nobody is; this channel's items are listed first, then unowned ones, then other channels'. The `nextStep` of a human or last-touched item is only expanded when this channel may act on it, and the digest budget is unchanged. The charter adds one rule sentence: 只推进分派给本频道或无人负责的事项；别的频道负责的事项不要改动，可以在正文提出建议. `context` gained `channelNames` (channel id → name for the project) so an agent can read the ids in `features[].ownerChannelId` and in other channels' records, and the `feature.upsert` receipt carries `ownerChannelId` (`null` once released).

**Working-tree isolation (未提交改动隔离).** Every finalized scheduled turn records an additive `Run.treeState` — `{dirty, files}` with up to 50 repo-relative paths from `git status --porcelain --untracked-files=normal` in the project directory, or `{dirty:false, files:[], unknown:true}` when there is no repository or git fails. The reading is read-only: the service never runs `git stash`, `git checkout` or any other mutating git command, and a failed reading never blocks anyone. `Engine.start` gates on it beside the existing review and project-serial gates: when the tree is dirty now **and** the project's most recent finalized scheduled run belongs to a different channel **and** that run recorded `dirty: true`, the channel does not start. A scheduled start is parked (`waiting`, `nextRunAt` = now + `intervalMinutes`) with one system event `工作树有频道「<name>」未提交的改动（n 个文件），等待其提交或清理后再开始` — written once per distinct wait, not on every tick — and a start a person asked for (`run`, and `resume`, which is scheduled work a human just requested) is refused with 409 carrying the same sentence. The same channel may continue on its own uncommitted changes, and a tree only a human touched never blocks: the gate needs a scheduled turn that recorded it dirty, so a clean last reading leaves the tree to the human. The bias is deliberately conservative — a recorded dirty turn keeps blocking while the tree stays dirty, even if the current changes are in fact someone else's — and it clears as soon as the tree is clean again.

**Turn note.** When the tree is dirty as a turn starts, the note adds one line `工作树有未提交改动：<最多 10 个文件>`, plus `这是本频道上一轮留下的，请在本轮结束前提交或清理，否则别的频道无法开始` when this channel's own previous scheduled turn recorded it dirty. The standing rule lives in the charter: 项目所有频道共享同一个工作树：本轮结束前提交或清理自己的未提交改动，否则别的频道无法开始.

## Native execution evidence and independent verification

`execution.prepare {command}` freezes a bounded source fingerprint before a command is executed by the existing native task, at the project root and in the current native turn. `execution.read {id}` returns the preparation and captured evidence. The agent does not submit stdout or an exit code. Morrow observes the exact native command's start and terminal events and stores command, cwd, output, exit code, native item/task/turn IDs, source fingerprint and provenance in SQLite. Prepared commands bypass renderer event coalescing so fast start/end events remain observable. A missing start, unknown exit code, truncated output, directory mismatch, source change or interrupted observation cannot certify success. Old native history cannot be attached retroactively as a new execution. Captured evidence is immutable through the work interface; restarted preparations remain unknown.

Native automatic approval can label the start event `source:agent` and the completion event `source:unifiedExecStartup` for the same command. Both accept the same strictly parsed literal shell wrapper, preserving exact command/task/turn/item matching and rejecting wrappers with appended shell operations. This is event compatibility, not automatic approval by Morrow; existing unknown evidence is not rewritten after the fix.

Expectations additionally accept `source:{kind:execution,command}` with a mandatory scalar rule, typically `/exitCode equals 0`. Rules use the actual native receipt. Execution evidence requires complete output and matching source fingerprints both during capture and at assessment; stale execution cannot certify the current source. File and HTTP evidence retain their original provenance. File capture proves the bytes collected, not that a reported command ran.

New choices use `evaluationVersion:2`. Their `decision.review` with `outcome:improved` first performs the existing field/window/guardrail checks, then requests independent verification. While verification is pending, failed or unknown, the response contains `pendingVerification:true` and `verificationId`; the decision remains active and its original contract is unchanged. `feature.upsert` requesting verified/resolved similarly remains investigating until verification passes. Final optional reports cannot bypass this gate. Legacy choices with version 1 or no evaluation protocol retain their historical interpretation; old records are not retroactively certified.

`verification.request {itemId?,decisionId?,evidenceIds}` can explicitly prepare this same gate. It creates a fresh native task through the existing Codex App shared runtime, with no project-work grant, approval policy `never`, a read-only sandbox and network disabled. The main channel/task binding does not change. The reviewer gets the frozen goal/expectations and original evidence, not the implementer's proposed success conclusion. It must inspect source and relevant counterexamples independently, and return exactly one result per expectation. No successful native command, missing checks, a blocking finding, source changes, malformed output, permission requests or abnormal completion prevent a pass. A recorded file change also stops verification. These are checks on native shell execution and the work interface, not a claim of a separate security boundary around arbitrary integrations loaded by native configuration.

The reviewer has a 5-minute timeout and a 4-MiB native event journal. It runs through native tools rather than service-side arbitrary command execution. The service only runs bounded, fixed Git reads for source fingerprinting. The journal retains initial native items and subsequent field changes/text appends without repeatedly charging accumulated output against the limit. Jobs, original prompts, model/task/turn IDs, raw events, conclusions, limitations and failed attempts persist. `verification.read {id}` returns the job, current-version validity and its events; project work views show compact results with the same feature provenance.

One reviewer runs at a time per service; pending work is serialized per project and each started review consumes the channel's existing UTC daily run budget. Queued/running reviews hold new autonomous turns in that project without spending a run, including turns made due by older reassessment signals; other projects can continue. Manual run requests report the pending review. This does not interrupt a turn already in progress when it submits its review or prevent user guidance through the native conversation. Further source edits invalidate the frozen review. A completed review signals the original decision/channel, respecting manual pause. Pausing stops its review; timeouts, connection ambiguity and restart keep unknown results and persist an intent to interrupt only that exact review task/turn. No uncertain send is automatically replayed. Identical current materials reuse their prior result. After resolving an environment problem, `verification.retry {id}` allows one additional attempt per identical material set per UTC day, preserving the previous unknown result and sharing the daily budget. Failed counterexamples require changed source/evidence. A validated decision.review or feature completion request is saved in `loop_finalizations`. After a pass the service revalidates current source, latest evidence and record revision, then applies the request transactionally without another native turn. Read `context.finalizations` for applied/stale/rejected status; an old requestId still returns its original pending response. Concurrent edits are never overwritten, and failed/unknown reviews leave the target unfinished. Durable terminal receipts drain after restart without repeating a model run.

The release gate has two halves. Per item: every feature in `itemIds` must have passed an independent review at least once, at whatever source version it was changed at; those verification IDs are retained in the sealed review contents. Per candidate: one **release-level** review must have passed on the current source version and cover every proposed item; its ID is retained as `releaseVerificationId`. The per-item *current-source* rule remains in force for completing an item (`feature.upsert` to verified/resolved and the report path), which is where it belongs; it is no longer charged once per item per release. A source change after a release-level review only requires redoing that one review, not every item's.

`verification.request {kind:"release", itemIds:[1..30], evidenceIds}` prepares it through the same mechanism as an item review — queueing, the read-only CLI session, the 5-minute cap, `unknown` handling, `verification.retry`, `verification.read`, finalizations and events. It refuses (409) while any named item has never passed a review, naming those items, and refuses (400) unless `evidenceIds` carries at least one execution-origin capture whose recorded source version equals the current source digest: the full check actually run on the candidate. It is bound to the source digest and item set at request time, so the same candidate and the same item set reuse their conclusion instead of paying for a second review — a passed one, and equally a failed or unknown one, exactly as an item review does: a counterexample is fixed in the source, and `verification.retry` remains the bounded way to attempt an unknown result again. Its reviewer prompt states that the subject is a release candidate, gives the candidate head and digest, each item with its latest passed review (id, the head/digest it was reviewed at, its summary) and the cited executions (command, exit code, output tail, bound version), and asks the reviewer to confirm read-only that those checks belong to the current source, to inspect the diff between each item's last-reviewed head and the candidate head (`git diff <head>..HEAD -- <paths>`, `git log`) for anything contradicting that item's review, and to run whatever read-only checks it can. The verdict format is unchanged: one `feature` check, no blocking findings and at least one real read-only tool check to pass.

Review records referenced by releases remain available beyond the recent-history limit, and an item-scoped work view also carries the release-level reviews covering that item. Publication still requires human approval of the exact sealed artifact and review hash, and uncertain publication is reconciled rather than resent.

Source fingerprints cover Git-tracked and unignored files, or bounded plain-folder traversal excluding common dependency/build/cache directories. The `source-v2` scheme excludes `node_modules` and `.pnpm-store` at every depth, including accidentally tracked dependency links, while retaining application assets and tracked build inputs. It hashes complete content and file modes, up to 5,000 files and 1 GiB, with a reusable 512-KiB buffer and a 5-second read limit. Application symlinks, submodules, special files, concurrent file changes and oversized sources fail explicitly. The scheme's distinct digest prefix invalidates older passes for current-source certification without changing historical evidence. These are before/after **source** fingerprints, not an immutable execution filesystem, dependency lock attestation, reproducible-build proof, deployed-version check or causal measurement. Independent model review can still miss errors. Existing metrics/contracts and independent feedback remain necessary; passing tests or review does not establish business uplift.

Before dispatching a decision review, the service mechanically checks that every planned source has a new observation in its original window, execution evidence binds the current source, and scalar rules are met. Late records cannot certify a closed window; missing/stale/contradictory fields are rejected before spending a reviewer run. The same constraints apply to current-proof lookup. A qualitative result still needs independent judgment. HTTP watch evidence preserves the complete response JSON, so rule pointers address its original fields rather than an invented `/value` wrapper.

New `acceptance-v2` reviews bind the project goal, current channel direction and immutable decision expectations. When structured expectations exist, feature title/progress description is context rather than acceptance criteria; standalone feature reviews continue binding the full description. A covered evidence subset reuses the latest review, including a failed result; it cannot select an older pass. New observations from planned sources are included and invalidate incomplete older reviews. Old records retain their original subject scheme and are not rewritten as successful.

Additive, idempotent tables: `loop_executions`, `loop_verifications`, `loop_verification_events`, `loop_finalizations`. Existing projects, settings, native bindings, pause states and original records are retained. The UI keeps the accepted compact shell, adds an expandable independent-review record, labels native versus file evidence, and displays the saved next direction after a decision is reviewed.

## Observation contracts and evidence-based review

New `decision.choose` calls require `expectations` (1–8 entries, including an `outcome`; a `stop` choice may use an empty list). Each entry contains `{id,kind:outcome|guardrail,claim,scope,source:{kind:file,path}|{kind:watch,watchId},verification,disconfirm,notBefore?,deadline,rule?:{pointer,operator:gte|lte|equals,expected}}`. A file may be a planned output that does not exist yet, but its canonical location must be inside the project. Watches must belong to this project and not be cancelled. Sources, conditions, rules and deadlines are frozen with the choice. `notBefore` defaults to the choice's creation time; delayed measurements must set it explicitly. Numeric comparisons require finite numbers and strict matching types. Rules operate on captured JSON, not model-reported scores.

Version 0.8 decisions carry `evaluationVersion:1` and an evidence insertion cursor. The cursor excludes pre-choice evidence even when timestamps coincide. New `decision.review` calls for these decisions require `assessment:{results:[{expectationId,verdict:met|not_met|unknown,reason,evidenceIds}],conditions:matched|changed|unknown,conditionReason,diagnosis:expected|pending|measurement|execution|assumption|environment|uncertain,explanation,adjustment:continue|observe|measurement|method|assumption|stop,understandingRefs?:[{id,revision}]}`.

Every original outcome and guardrail must be represented exactly once. Evidence must come from its frozen file or exact HTTP watch, be newly collected inside its observation window, and include the latest qualifying observation from that source. Agent-authored evidence cannot stand in for collection. Missing data, invalid field types and premature observations cannot establish a conclusive result. Rules mechanically check the captured scalar and reject a conflicting declared verdict; qualitative interpretation remains explicitly attributed to the agent. `improved` requires every outcome and guardrail to be met. `not_improved` requires an actual unmet expectation. Changed/unknown comparison conditions and pending/broken measurement permit an inconclusive review, retaining the measured values. An uncertain causal explanation does not erase an otherwise observed outcome.

Reconsidering an assumption requires saving a new or revised project understanding first and citing its current revision; referenced original assumptions must have advanced in version. The assessment, evidence references and original plan are saved transactionally in SQLite, with immutable revision history and idempotent replay. Memory search also includes expectation scope, disconfirmation and assessment explanations. These changes do not train native model weights, independently establish causality, or guarantee that the agent's chosen metrics represent all user goals.

Captured evidence from an expected source signals its dependent decisions without unpausing work. For a new HTTP expectation, one fresh sample is retained even if the watched value has not changed since the old baseline. Changes to other JSON fields explicitly referenced by expectation rules are also retained; unchanged valid samples remain quiet. Captures now retain `watchId`. Old HTTP evidence is not retroactively assigned to a watch. Expectation deadlines participate in reassessment scheduling.

Existing decisions without `evaluationVersion` retain their previous review protocol and are labelled as historical textual reviews in the UI. They are not backfilled with invented observation contracts. This increment adds JSON fields to existing tables and preserves old projects, native bindings, settings, pause states and records. The project judgment document and associated feature expose the same compact, expandable `预期与实际` record; no new configuration form is introduced.

## Project understanding and decisions

New projects start with one paused `自主推进` responsibility and a 32-run daily limit; existing channels are untouched. The native agent chooses strategy. The framework persists its basis, alternatives, expectations, review boundaries and subsequent assessments.

- `understanding.upsert`: `{id?, revision?, kind:fact|assumption|unknown|capability|constraint, title, statement, relevance, verification, status:active|invalidated|retired, evidenceIds, reviewAt}`. Facts and invalidations need evidence references, which retain their original agent/file/HTTP provenance. This does not independently certify the statement. Updates require the current revision; duplicate titles reuse the original record. Each version is saved.
- `decision.choose`: `{objectiveVersion, options:[{title,kind:act|investigate|build_capability|observe|stop,benefit,cost,uncertainty}], selected, rationale, nextStep, expectedOutcome, evaluation, stopWhen, expectations, understandingRefs:[{id,revision}], memoryRefs?:[{kind,id,revision,use:apply|adapt|avoid|not_applicable,reason}], evidenceIds, watchIds, reviewAt, maxRuns, itemId?}`. One current choice per channel; active choices cannot duplicate a feature or title across channels. A fresh goal/direction hash and current, unexpired understanding revisions are required. Original choices and goal snapshots are immutable.
- `decision.review`: `{id,revision,outcome:improved|not_improved|inconclusive|abandoned,conclusion,evidenceIds,nextDirection,assessment}`. Closes the choice, retaining its original expectation and assessment separately. New decisions follow the observation contract above; legacy decisions omit `assessment`. The overall interpretation is still an agent assessment, not a claim of independently measured business impact. Afterwards the agent can choose another action, observation or stopping point.
- `memory.search`: `{query?,kind?:understanding|decision|learning,limit?:1..30,offset?}` searches all project records with literal, space-separated terms and bounded pagination. Results retain status; invalidated/retired entries are historical lessons, not current facts.
- `memory.recall`: `{query?,itemId?,limit?:1..12}` ranks project records by local lexical relevance and association with the same feature. It searches the full current memory corpus, including retired/refuted knowledge and reviewed failed decisions, without a recent-record cutoff. Chinese bigrams and other word tokens are supported. Automatic recall uses the goal, direction, current focus and selected action; a specific query can refine it. Matches carry status, revision, source references, excerpts, cautions and matching reasons. Ranking is neither semantic understanding nor a confidence/causality score. Use `memory.read` to check full content and conditions.
- `memory.read`: `{kind,id,beforeRevision?}` returns the full scoped record and up to 20 historical understanding/decision/learning versions, with a continuation cursor. Learning mutations now save immutable snapshots; the first update of a legacy entry preserves its currently available revision before writing the new one. Earlier missing snapshots are not invented, and the existing audit trail is retained.

`memoryRefs` records the agent's actual applicability assessment, not every automatically retrieved suggestion. Up to 12 unique references retain their exact revision, a bounded historical snapshot and the reason for applying, adapting, avoiding or judging the experience inapplicable. Current project ownership and revision are checked transactionally. Active decisions cannot be cited as reviewed experience. Direct `apply` rejects invalidated/retired/refuted/stopped records, expired understanding and failed/abandoned decisions. `adapt` remains possible with an explanation and a new decision's evaluation; this permits deliberate re-experimentation without treating the old result as success. The assessment is agent-authored, not proof that retrieval caused a better outcome.

`context.strategy` includes the exact goal/direction version, daily budget, bounded previews, active choices and review reasons. Its `relatedMemory` presents up to six relevant records before the larger history sections. Long fields are marked `truncated`; `counts` and `partial` expose omitted strategy records. The outer `learning` list now contains the latest 12 bounded summaries with `learningCoverage` counts; full history stays in SQLite and is retrieved through `memory.recall/search/read`. Desktop `GET /api/projects/:id/work` retains its existing record coverage and includes the compact 当前判断 document, with expandable experience references and their original evidence.

New native guidance, relevant observation/release signals, changed or expired understanding, changed goals, review deadlines and spent attempt rounds require reassessment. Signals and run attribution survive restart. Signals received during a running turn remain available to its next context; manual pause always wins. At completion, an active choice's review time can shorten an existing wait. Observation/stopping choices wait for feedback or their review time instead of consuming an attempt budget in a polling loop. Once reassessment is due, `feature.upsert` and `release.propose` reject until the choice is reviewed; evidence collection, understanding updates and review remain available. This gate governs the Morrow work interface, not arbitrary native shell commands. Existing native permissions and the separate daily scheduler budget remain authoritative.

Revisions to cited experience also wake dependent channels and require review, except references explicitly judged `not_applicable`. An understanding reference that was current when chosen carries its review deadline into scheduling. An already-expired record deliberately cited for historical adaptation does not immediately force an endless review; it retains its caution and still requires reassessment when revised. Reference snapshots never change when their sources are updated. Existing decisions without `memoryRefs` remain readable and usable.

Additive tables: `strategy_understanding`, `strategy_decisions`, `strategy_revisions`, `strategy_runs`, `strategy_signals`. Mutations use the same expiring scope, transactional idempotency and project isolation as the existing work interface. No automatic skill registry, cross-project memory transfer, autonomous channel reorganization or general deployment adapter is claimed by this increment.

## Existing work and publication interface

`POST /api/agent` uses a private, expiring run grant distinct from the desktop credential. The grant identifies one project, channel and active run. `context`, `contract` and `evidence.read` are read operations. Mutations require a stable `requestId`; the mutation and cached result commit in the same SQLite transaction. Replays return the same result, different payloads under the same ID conflict, and fresh operations after the run ends are rejected.

`context.project` carries `id`, `name`, `goal` and `briefRevision`, and `contract.briefRevision` repeats that version; the brief (项目说明) is the user's own written requirements (goals and success criteria, users and scenarios, current stage, priorities and non-goals, resources and entry points, constraints, pending decisions), ranks above the agent's own inferences and is never edited through the work interface — conflicts or gaps are raised as specific questions in the reply. Its text reaches a scheduled turn in the task charter, resent whenever a new version is saved; each saved version (`PATCH /api/projects/:id`, desktop credential only) changes the objective version, records a reassessment signal for the project's active decisions and wakes its enabled channels.

`contract.nativeCapabilities` lists what the native Codex App actually offered a Morrow-scheduled turn, as measured on 2026-09-09 by one real turn: `{id, name, status: available|unavailable|partial|untested, measuredAt, note, howTo}` per entry. It is a dated record of that single probe, not a live query and not a permission grant: nothing is re-checked at runtime, `untested` means no measurement exists rather than "probably works", and an entry never authorizes reporting an observation the turn did not actually make. The task charter points at this operation for the dated inventory instead of repeating it. As measured: Computer Use (`@oai/sky` over `node_repl`), web search and this work interface are available; native memory is readable but written by the App itself after a session; the in-app browser plugin returns no browser inside a Morrow-created thread; Chrome/Edge through the ChatGPT browser extension and an explicit `agent.browsers.get("iab")` were never tried.

`context.budget` carries the scheduler and usage limits that apply to the turn: `runsToday` and `maxRunsPerDay` for the channel's UTC daily budget, and `usage` with the latest account reading (`reading`, per window `usedPercent`/`resetsAt`; `stale` when older than ten minutes or past its reset), `unknown` when no reading exists, the global `reserve` (`window`, `keepPercent`: automatic work stops once the account reaches `100 − keepPercent`), and the project `project` cap (`window`, `limitPercent`, `usedPercent` estimated from the account readings taken before and after Morrow's own runs). Limits are enforced by the scheduler before a turn or review starts, never mid-turn; the same numbers appear in every turn note so the agent can prefer cheap, informative work or wait when usage is tight.

Operations: `feature.upsert`, `evidence.record`, `evidence.capture`, `learning.upsert`, `watch.create`, `watch.cancel`, `wait`, `release.propose`. Item and learning updates use revisions. Evidence distinguishes agent statements, actual file capture and HTTP capture. `context` lists evidence provenance and `bytes` without its content; `evidence.read` returns the preserved content.

`GET /api/projects/:id/work?itemId=...` returns shared observations, learning, watches and releases. `POST /api/releases/:id/review` accepts the desktop credential, exact `reviewHash`, `approve|reject`, and optional feedback. The agent grant cannot call this endpoint. `POST /api/releases/:id/reconcile` checks an uncertain outcome without resending publication. `GET /api/releases/:id/script` returns the sealed script text and digest of a `local-script` release so a human can read exactly what an approval would run; it also requires the desktop credential and returns 409 for an HTTP target.

Release preparation copies a project-contained artifact (up to 8 MiB) into private storage and binds its SHA-256, target, checks and review text. The HTTP adapter sends `POST {releaseId,reviewHash,artifact:{name,sha256,bytes,base64}}` with `Idempotency-Key: releaseId`. A receipt must match `releaseId` and `artifactSha256` and report `status: published|failed`. The GET status endpoint receives a `releaseId` query parameter and returns the same receipt. A lost or mismatching response stays unknown; recovery queries status rather than reposting.

A target has one of two shapes. `{kind:'http'|omitted, url, statusUrl, label}` is the adapter above. `{kind:'local-script', label, script, args, timeoutSeconds, statusScript?}` names a script the human wrote and **already committed inside the project**; it is never written, generated or edited through the work interface, and the agent may only reference it by path. `script`/`statusScript` are project-relative paths to regular files of at most 256 KiB whose resolved location must stay inside the project, so a symlink pointing outside is rejected. `args` holds at most 16 strings of at most 1000 characters, passed to the process as an argv array and never through a shell; `timeoutSeconds` is an integer 30–3600; `label` is at most 100 characters. Preparation seals a copy of the script(s) next to the sealed artifact, computes their SHA-256 into `target.scriptSha256`/`statusScriptSha256` and therefore into `reviewHash`. The agent cannot supply or revise a digest, and editing the project's own file afterwards does not change what will run. Approval re-checks the sealed digests and refuses with 409 on a mismatch; a mismatch discovered at publication time records `failed` without executing anything.

Only after a human approves the exact sealed script and review hash does Morrow run that sealed copy — never the project's file — from the project root, with standard input closed and a fixed environment holding only `PATH`, `HOME`, `NO_COLOR=1`, `TMPDIR` (optional: forwarded only when the service itself has one, so the script's temporary files land where the service's do instead of `/tmp`), `MORROW_RELEASE_ID`, `MORROW_ARTIFACT_PATH` (the sealed artifact copy), `MORROW_ARTIFACT_SHA256`, `MORROW_REVIEW_HASH`, `MORROW_PROJECT_PATH`, `MORROW_RECEIPT_PATH` (fixed at `<home>/releases/<id>/receipt.json`) and `MORROW_RUNTIME_CACHE` (`<home>/runtime-cache`). The service token and the rest of the service environment are never passed. Exit code 0 plus a last non-empty stdout line in the same receipt shape (`{releaseId, artifactSha256, status: published|failed, …}`) settles the release. A non-zero exit, unparsable output or the timeout (SIGTERM to the process group, SIGKILL after 5 seconds) leaves it `unknown`, exactly like an HTTP response that could not be confirmed. Combined stdout/stderr is kept as `log`, bounded to its last 1 MiB and redacted; `context` shows only a tail of it. Reconciliation reads the receipt file first, then runs the sealed `statusScript` with a 60-second cap, the same fixed environment and no arguments, and otherwise stays unknown. A restart turns `publishing` into `unknown`; publication is never re-run automatically. This is the one place where Morrow executes a command a work-interface record points at, and it remains a human-gated installation step, not a general command channel or a claim that the script's own actions are sandboxed.

### Installed build identity and the automatic version switch

A `local-script` release usually installs Morrow itself. A build writes a read-only `Contents/Resources/build-info.json` into its bundle carrying `commit` and a stable **whole-bundle fingerprint** over the service TypeScript, the compiled main/preload/renderer output and the package metadata — excluding that file and every signature, so signing twice is not a new version while a pure interface change is. The daemon and the Electron main read it once at start and keep it in memory as the build they are running; a missing or malformed file reads as `unknown`, and a development checkout (no `.app` ancestor) never participates.

`scripts/release-local.sh` adds two optional receipt fields after a successful install: `installedBundle`, the absolute path of the `.app` it replaced, and `buildFingerprint`, read back from the freshly installed bundle's build-info. `receipt()` validates them (absolute path, at most 4096 bytes, hexadecimal fingerprint) and stores them on the release; anything else is dropped rather than kept as a version. Neither the script nor the service restarts anything as part of publication.

In the same transaction as the `published` write, the service decides whether that receipt describes **its own** bundle: only a `local-script` target whose `installedBundle` resolves to this daemon's own bundle path with a fingerprint different from the running one creates a persisted `upgrade` record `{releaseId, targetCommit, targetFingerprint, installedBundle, fromBootId, phase:'pending'|'draining'|'exiting'|'blocked'|'applied', requestedAt, blockers?, error?}`, one per target fingerprint. The same fingerprint reinstalled over itself is recorded `applied` without restarting. An HTTP target, another project's identically named script that installed elsewhere, a missing or malformed identity, and a duplicate receipt create nothing: identification is the bundle path plus the fingerprint, never the script's file name. `native/status.restartRequired` keeps its own unrelated boolean meaning.

While a record is `pending`, `draining` or `exiting`, every entry point that would **start** work is refused with a 409 naming the switch: manual `run`/`resume` (a scheduled start parks and re-checks instead, with one system event per channel per switch), a chat send that would start a native turn, `verification.request` and `verification.retry`, release approval, and `POST /api/releases/:id/reconcile`. Pause, interrupt, answering the task's own questions, every read and declining a release stay available; a review already queued still runs to completion, and a release approved earlier waits for the new daemon instead of starting its script during the drain. A `feature.upsert` to verified/resolved (or a `decision.review` reporting `improved`) needs a new review, so it is refused the same way and nothing is written — the turn can record its progress without completing the item and complete it after the switch. Idleness is read from real state, not `channels.status`: no active CLI run, no native turn starting/scheduled/active, no send the task has not accepted, no queued or running review, no publication in flight. Ten minutes is a reminder deadline only — the blockers are then recorded for the interface and the switch keeps waiting; nothing is ever interrupted.

`GET /api/upgrade` (desktop credential) returns the running identity (`bootId`, commit, fingerprint, bundle path, data directory), the dedicated exit code, whether the service is idle now, the live blockers and the record; the same object is in `/api/state` as `upgrade` for the polling interface. `POST /api/upgrade/acknowledge`, `/restart` and `/blocked` are the handshake, desktop credential only and idempotent: each carries `{fromBootId, targetFingerprint}` and is refused (409) unless both match this boot and the current target. `acknowledge` says the local Electron main verified identity and target and will restart itself; `restart` lets the interface ask for the same handshake early and is refused with the blocker list while work is still running; `blocked` records a handover failure (`reason`, at most 500 characters). The work grant cannot reach any of them (401), so an agent can never trigger a restart.

When idle and acknowledged, the daemon sets its internal exit flag before writing `exiting` — with no await in between, so a publication or turn cannot slip in after the check — then stops accepting requests (everything else answers 503 with `code:'upgrade_exiting'`), drains in-flight requests within a bound, runs the existing close path (engine, loop, native, HTTP, store, lock) and leaves with exit code 75. The Electron main waits for the old daemon to be really gone (its own child's exit event, or an adopted daemon's lock release plus health going offline) and only then relaunches this app, at most once per target. A new daemon reconciles on start, before any scheduling: the target fingerprint now running becomes `applied`, a still-old fingerprint becomes `blocked` with its reason, and the existing recovery (publishing → unknown → reconcile from the receipt file, native turns re-synced) follows unchanged. The first installed version carrying this logic still needs one manual switch to enable it.

HTTP JSON observations are bounded to 512 KiB with a 10-second timeout, explicit JSON Pointer, at least 30 seconds between polls and up to 50 active monitors per project. `continuous` defaults to true: after a condition is triggered or a review deadline expires, changed values still produce evidence and wake the enabled source channel. Identical values stay quiet. `continuous:false` makes an observation end after its condition/deadline. Cancellation or pausing the channel stops scheduled collection. Waits may refer to another channel's source in the same project.

`watch.create` also accepts `kind:'file', path:'relative/project/file.json'` instead of `url`. Omitted `kind` preserves HTTP behavior. File paths are stored as canonical project-contained paths; the root itself, paths outside it, symlink components (including dangling links), and non-regular files are rejected. Each poll rechecks the path and reads at most 512 KiB. Missing files quietly wait without evidence or an error wakeup; normal deadline reassessment still applies. For a `changed` watch, a file present at registration produces a quiet first baseline; a file absent at registration wakes the channel on its first appearance (even if it appears before the first poll). Nonempty file pointers compare the selected JSON value with object keys ordered recursively; object-key order is irrelevant, while array order and element values remain significant. Empty file pointers compare complete file bytes. HTTP comparison is unchanged. Reappearance with the same previously observed value stays quiet. Registration-time absence is saved separately from current availability. Existing rows with a selected-value baseline continue from that value, avoiding a spurious wakeup when upgrading from the earlier whole-file comparison.

File evidence has `origin:'file'`, the canonical path as `source`, the raw-byte SHA-256 as `digest`, parsed JSON (or plain text for an empty pointer) as `data`, and the selected `pointer` and `value`. A non-JSON file with a nonempty pointer produces one audit/wakeup per repeated error, and can recover on later valid content. Both a file expectation naming that same path and a watch expectation naming that watch can use these records. A newly created expectation obtains one fresh sample even when the old baseline is unchanged; unchanged subsequent samples stay quiet. No command watch is supported: execute commands through `execution.prepare`, then watch their output file.

Parsed file JSON must contain only finite numeric values, including nested or unselected fields. An overflowing number such as `1e400` is rejected before evidence or `lastValue` is stored, so JSON serialization cannot silently turn it into `null`. This is a stable collection error; repeated identical errors stay quiet and later valid data follows the normal recovery path. Quoted strings such as `"1e400"` remain ordinary strings.

`loop_grants`, `loop_calls`, `loop_evidence`, `loop_learning`, `loop_watches`, `loop_waits`, `loop_releases` are additive SQLite tables. Native executions retain their exact task/turn IDs. Scheduled turns use App follower IPC. Native channels inherit the App task permissions and approval settings; explicitly narrowed scopes retain their policy and scope checks. Automatic sends never steer an unexpectedly active user turn. Tasks must be created and loaded in the App, then explicitly associated. Independent review uses an official read-only ephemeral CLI session; account usage is queried separately without a model turn.

### Unknown-review retries

An explicit retry carries the latest unchanged completion intent into the new review, preserving the original rejected intent and original run reference. Concurrent target changes or newer intents prevent carrying it. Bounded successful tool observations from the prior attempt may guide the retry; they never count as this attempt’s independent check or a passing verdict. The same-material daily retry limit and review timeout remain unchanged.

### Desktop review history

`GET /api/projects/:id/work` includes `verificationHistory:{hasMore,cursor,revision}`. Its initial review selection contains the most recent 30 records, up to 30 distinct subjects' latest reviews (feature, otherwise decision, otherwise channel), and existing release references. `?verificationBefore=<id>` reads the previous 30 records in durable insertion order with their referenced evidence; foreign project/item cursors are rejected. The cursor follows the recent page, not the additional pinned rows, so pinned older reviews cannot make intervening history unreachable. The desktop merges pages by ID and invalidates cached pages when the project/source revision changes. This is a read-only display path: original verdicts, prompts and evidence are not rewritten, prompts stay out of the response, and the agent `context` retains its previous review limit.


## Native tool evidence snapshots

`evidence.native {before?, limit?:1..20}` lists stable tool item IDs for the current run's bound native task and channel, filtering by project/channel/turn ownership and recognized native tool type before pagination. A fallback role of `tool` alone is insufficient (for example, reasoning records are excluded). It is read-only and needs no request ID. `evidence.link {itemId?,summary,nativeItemIds:[1..20]}` reads those existing records and stores an immutable `origin: native` evidence snapshot through the usual idempotent write request ID; it does not execute a native tool. Foreign tasks/channels, unknown or withdrawn items return 404. Duplicate IDs and invalid counts return 400; a mixed invalid batch stores nothing. The original direct CLI and the per-run launcher support both operations.

Each snapshot records stored IDs, thread/turn, tool and target, bounded sanitized input/output text and digests, plus image references. When the native receipt has `raw.error`, a separate bounded `error` summary preserves it alongside any partial output; failures are not reduced to an empty result. Known service secrets and sensitive keyed fields are redacted. Summary text is capped at 6000 characters per input/output and explicitly marked truncated for length or depth limits (`truncationReasons`). `sha256` hashes the sanitized representation before display-length truncation; `sourceSha256` hashes the original stored field JSON, so omitted deep content changes remain distinguishable without exposing that content. These are receipt fingerprints, not execution-success or truth attestations. Inline image data is retained (384 KiB aggregate encoded data, 20 references maximum); oversized snapshots fail with 413, with a final 512 KiB byte bound. External/local image URLs or paths remain `reference_only` and are never fetched: their future availability is not guaranteed. References above 4096 bytes are rejected with 413 rather than shortened; known-credential redaction is marked with `redacted`. Inline base64 image URLs (including `image_url.url`) share the same supported MIME and aggregate size limits as MCP image data, and retain their full encoded content. Copying a receipt keeps it readable via evidence.read after a native projection changes or disappears. Capture time is not asserted to be the tool execution time.

The UI labels this source 原生工具记录, distinct from execution evidence. Native origin proves which stored native receipt was linked; it does not establish successful execution, complete layout validation, deployed state or business impact. In particular it cannot replace the source-bound execution evidence required by a release.
