## 核心设定：让 Codex 自主承担项目目标

2026-09-08 用户在讨论自主理解、决策、能力建设、效果判断、经验复用与工作协调之后确认：“确实是的，最主要的你要记住这种设定，激发框架的能力”。此设定是长期产品原则，不限于下一次功能迭代。

用户提供初始项目、期望结果、可用资源和授权边界。Codex 应主动理解项目、提出并选择有价值的行动、执行和验证、依据真实反馈调整策略；Morrow 为这种自主性提供持续工作的条件。用户不需要先设计部门、流程、频道、技能目录或持续分配下一项任务。用户的工程与运营例子是自主性要求的说明，不能成为系统可探索方法的上限。

### 必须支持的能力

1. **理解并修正项目认识。** 持续认识产品服务谁、解决什么问题、所处阶段、系统与线上环境的关系、资源与约束，区分事实、推测和未知。根据阶段决定投入方向，避免每轮重新调查或机械找 bug。
2. **自主选择下一步。** 比较直接改进、获取信息、补齐能力、继续观察和停止尝试的价值，综合预期收益、证据强弱、成本与可逆性。保留有预算约束的探索空间，允许提出人未交代的方法；信息不足时先减少关键不确定性，结果不支持时改变策略。
3. **建设自己的工作条件。** 主动识别并在授权范围内补齐观测、测试、反馈采集、复现、发布和分析工具。同步改善产品与完成工作的能力，根据后续价值决定投入，避免无限建设基础设施或制造技能。
4. **判断真实效果。** 将行动、预期、实际结果和后续判断关联，考虑反馈延迟和其他影响因素；证据不足时保留未知，反例出现时纠正旧结论。代码通过测试、发布成功和关闭的工作项数量不能替代业务成效。目标需保留不能牺牲的体验、成本与信誉约束；执行者不能通过改写历史目标、原始证据或评价口径制造成功。
5. **让经验改变后续行为。** 知识与技能从实际工作中提炼，保存依据、适用范围、版本与失效条件，在相关决策中检索和使用，允许修订、淘汰和回退。一次结果不能自动升级为普遍可信技能；跨项目复用必须重新判断适用性。衡量是否少犯同样错误、提高有效尝试的效率、降低达成目标的成本，而非累计记录或技能数量。这是外部记忆与工作方法的改进，不等同于训练模型权重。
6. **协调资源并掌握工作节奏。** 项目统一协调工作优先级、预算、共享知识和修改冲突。频道承载持续职责，可随实际工作需要形成、调整、合并或结束，保持同一项目的共享看板及 feature 来源可追溯。新证据到达时继续、等待效果时保持安静、无效方向及时停止；持续运行不能等同于持续消耗资源。

### 框架与人的职责

策略与方法由 Codex 根据项目事实形成。框架提供可调用的工作能力、上下文与记忆检索、真实反馈、可靠唤醒与恢复、项目协调、预算约束及可审计的记录；上线确认与原始证据的保护不能依赖执行者自觉遵守。失败或连接恢复后应能继续已有工作，不能重复发布、丢失判断或悄悄创建替代任务。

用户界面继续保持简单：项目、目标、连续对话、真实状态和项目统一看板。用户随时指导或暂停，日常工作由 AI 自动管理。已有授权范围内不增加逐项确认；发布准备完成后展示明确版本、变更、收益预期、验证依据、影响和回退方案，由人确认上线。确实缺少无法自行取得的资源或需要用户决定目标取舍时，集中说明缺口与所需决定，不把普通探索和实现问题重新派回用户。

### 后续优先级与验收

优先把“理解项目 → 选择值得做的事 → 获取可信反馈 → 调整下一步”做扎实，再让知识和技能从实际工作中形成并经验证复用。增加提示词、调度轮数、固定工作流、卡片或知识库本身不算达成设定。

验收使用陌生的隔离项目，只提供目标、资源和约束，不预先告诉 Codex 要发现的问题或应该采取的策略。引入需求变化、无效实验、反例、过时知识、资源限制或运行恢复，观察它能否自主识别关键信息缺口、选择有依据的行动、补齐必要能力、修正旧判断、协调工作并合理等待或停止。以实际效果、判断质量和资源成本评价，不以任务、运行、文档或技能数量评价。

## 项目与频道

项目对应用户打开的文件夹。一个项目只有一份统一的功能看板，包含 feature、问题、机会和假设。每个工作项有项目内稳定编号、来源频道、后续参与频道、证据和修改记录。不同频道可以共同推进同一个功能；频道仅定义长期职责、目标、节奏和运行上下文。频道中的看板入口应回到项目统一看板。

## 频道是 Codex 主动工作的长期上下文

2026-09-07 用户纠正：每个 channel 都是在为 Codex 主动工作做准备，用户可以中途通过对话接入和指导。用户期望 Codex 自主判断、提出下一步并推进工作，而不是自己操作复杂的配置、调度和运行页面。

频道应围绕一个长期关注方向，积累项目背景、用户指导、已做的工作和待验证的想法。它是同一个项目中 Codex 持续工作的上下文，不是要求用户逐条派发任务的工单容器。Codex 根据方向、当前项目事实和已有对话选择值得推进的下一步，执行、验证、反思并继续；应能说明为什么做这件事。用户的对话是对正在工作的 Codex 的指导，后续自主轮次继续沿用这些指导；不能另开一套“人工备注”或丢失原生会话。

Morrow 的职责是准备上下文、在合适时机唤醒 Codex、保存工作连续性和记录，并维护项目统一看板。自主选择和执行由 Codex 完成，不由 Morrow 硬编码一串巡检任务。长期方向不等于固定周期重复同一提示，也不应把每次工作都包装成必须由用户查看和管理的“运行”。内部的预算、等待、权限、失败恢复及持久化继续存在，但不成为频道的主界面。

频道主界面以一个清楚的工作方向、一条连续对话和真实工作状态为中心，用户主要做方向指导和暂停/继续。Codex 主动呈现正在做什么、依据是什么、结果如何及下一步；没有实际工作时不能编造“思考中”或进展。运行批次、会话 ID、连接协议、频率和底层日志进入按需展开的详情。保留用户已认可的灰白紧凑外壳，不再增加卡片式管理界面。现有项目方向、暂停状态和数据不能因重新设计被批量改写或自动开始执行。

0.5.0 的已实现基线：首页显示工作方向、连续对话和开始/暂停/继续；参数、运行记录及原生连接放入工作详情。连续工具记录默认归入可展开的“工作过程”，自主上下文及机器可读安排保留完整内容但不占据对话正文。开始工作会准备唯一原生任务并提供项目上下文。Codex 在完成有意义的步骤后给出持久化的下一步安排：继续推进、等待指定时间或提问等待指导。继续推进至少间隔 30 秒并受已有预算限制；缺少有效安排时回退到保存的复查间隔。等待指导时，两端的原生回复都可恢复后续工作；用户手动暂停后不会被普通对话自动开启。已有目标、权限、预算、暂停状态和历史保留。新频道默认预算为 32 次，仍可在工作设置调整。用户随后明确指出，这一机制仍未达到其产品期望，不得将上述实现记录理解为自主工作能力已获验收。

## 对结果负责与开放探索：最新产品纠正

2026-09-07 用户进一步纠正：期望 Codex 围绕目标持续发现并尝试用户没有逐项交代的方法，承担过去需要人判断和推进的工作。用户举例，系统查完 bug 后仍需上线、主动建立功能反馈、发现线上问题并优化；运营需要围绕吸引用户付费主动获客、追踪流失原因、验证改进。上述例子说明自主性的要求，不是需要固化成产品流程的完整任务清单。用户自己的经验也不应成为 Codex 探索方法的上限。

项目目标应驱动持续工作：Codex 自主判断什么算有效进展、当前缺少什么事实、哪些办法值得尝试；缺少反馈时，应识别并建立必要的观测和验证能力。在已有授权和可用资源范围内采取行动，追踪实际后果，根据证据修正判断、改变策略或停止无效尝试。完成代码修改、通过测试、执行成功和看板关闭分别只是过程事实，不能自动等同于产品稳定、用户愿意付费或其他目标已经改善。

频道继续作为项目下可对话、可指导的原生工作上下文，其划分不能阻止跨领域推进同一个目标。项目需要共享已经知道的事实、尚未验证的判断、尝试及其结果，避免各频道独立重复调查、互相矛盾或只优化自己的局部指标。用户主要提供目标与必要背景、资源和约束，随时指导；不应承担设计整套流程、持续派发任务和逐次提醒收集反馈的工作。

0.5.0 的下一步文本、原生历史和定时唤醒只是连续执行的基础。当前实现尚缺少持续维护的目标成效、可追溯的假设与尝试、预期和实际结果的对照、外部反馈接入及根据这些证据调整策略的机制。仅增强“主动工作”提示词或增加自动运行次数不能算完成本轮要求。新方向的验收应覆盖：用户只给目标，Codex 发现未告知的问题或信息缺口，建立必要反馈，实施有依据的尝试，并在结果不支持原判断时主动调整；必须区分已实现、隔离验证和真实环境验证。

后续机制设计需要支持按项目保存、可撤销的持续授权和资源范围，使部署、数据读取或对外运营等能力在获得相应授权后能够进入工作闭环。当前实现中的一律禁止外部动作不能被当作最终产品能力边界；用户举例本身也不代表已授权操作任何线上系统或发送外部消息。此次记录只更新产品要求，不修改现有项目权限、暂停状态或运行行为。实现继续保留用户已认可的紧凑界面、同一原生任务和 SQLite 持久化。

## AI 自动闭环与上线确认

2026-09-07 用户明确确认：整个系统由 Morrow 通过 Codex 自动管理，人只在上线时审阅并确认。项目在已有资源和授权范围内，由 AI 自主发现机会、建立和维护 feature、调查、实现、测试、准备发布，以及上线后收集反馈、评估效果和继续改进。常规工作不增加逐项确认，不要求用户手动建卡、改状态、整理证据或提醒下一步。用户仍可随时通过原生对话指导或暂停工作。

项目唯一看板承载每个 feature 的完整追踪：目标与提出依据、来源和参与频道、尝试与修改、测试和发布版本、实际效果及后续判断。同一 feature 跨频道、跨运行保持同一记录；每次执行关联到相应 feature，不重复生成卡片。看板与记录由 AI 自动维护，状态必须有实际证据支撑。上线是生命周期中的一个节点，后续反馈继续归入同一 feature。

上线确认应发生在实现、必要验证和发布准备已完成之后。AI 自动生成具体、可审阅的发布说明，至少包含：这次改了什么及关联 feature、为什么改、预期收益及其依据、已完成的验证及尚未验证之处、影响范围和回退方案，以及上线后衡量效果的指标与观察条件。预期收益与已观测收益明确区分；没有数据支撑时不得编造量化提升。

用户确认对应明确的待发布版本与变更范围，系统只发布已确认内容；实质新增或改变的发布内容重新形成待确认版本。确认记录、实际发布结果和后续观测在 SQLite 中关联保存。用户确认后，系统自动执行该次发布、验证和效果跟踪；未获确认时保持待发布状态，其他不依赖发布的工作仍可继续。反馈形成新的改进并完成准备后，再提交下一次上线确认。

这是本轮明确的目标行为，当前 0.5.0 尚未实现完整闭环及发布确认机制。后续验收必须覆盖 AI 自动维护 feature、准备真实发布说明、未经确认不执行上线、发布内容与确认版本一致，以及上线反馈驱动后续改进。

0.6.0 实现记录：原生 Codex 调度轮次获得按项目与运行限定的工作接口，可在执行中维护 feature、采集证据、修正目标/假设/尝试、登记反馈条件和等待安排。发布准备封存产物和审阅内容，App 按明确版本接受人工确认，AI 工作接口不能批准上线。第一种发布接入为项目提供的 HTTP 发布端及回执查询端，反馈接入为 HTTP JSON 观测；文件证据和反馈自动关联回原 feature。发布结果不明确时只核对回执，重启不重复发送发布。保留已有权限、暂停状态与原生会话；新增可显式选择的 Codex 原生权限模式。当前通过隔离机制与界面测试验证，不代表已完成真实模型自主性或真实业务收益验收；实际项目还需接入其部署与数据能力，原生后台连接也必须真实就绪。

## 原生运行时与持续机制

2026-09-07 补充确认：Codex 接入必须与 macOS Codex App 使用同一条原生会话并双向同步。用户在 Morrow 发送的消息直接进入该原生会话，在 App 中发送的消息、回复及运行活动也在 Morrow 中同步呈现；重连后补齐历史。仅调用独立 `codex exec`、复制会话文本或打开终端续接，不满足这个要求。登录、模型、工具和执行继续由原生运行时管理；接入状态必须基于实际连接，未验证同步时不得显示“已同步”。

2026-09-07 后续补充：用户在 Morrow 对话时，不应再手动打开 Codex App 中对应的任务。后台创建、恢复和连接任务属于 Morrow 接入层需要解决的能力；「在 App 中打开」只能是可选入口。0.4.2 的验收仅证实已加载任务的双向同步，没有覆盖未加载任务或 App 重启后的后台恢复，不能据此声称独立对话体验已完成。

0.4.3 接入改为共享由 Codex App 启动的同一个原生后台：一次性设置 `CODEX_CLI_PATH` 启动桥接，原样保留 App 传入的参数、环境、MCP、模型与权限，只把 stdio 通道转换为私有 Unix WebSocket，再透明转发给 App。Morrow 作为第二个客户端直接创建、恢复和观察原生任务；已有任务保持同一线程与轮次 ID。桥接随 App 生命周期退出，Morrow 断开或重启不会终止原生后台。设置在下次打开 Codex App 时生效，并通过用户登录启动项延续，支持撤销。切换前保留旧 owner/follower IPC；旧通道仍只能访问 App 已加载的任务，不能显示后台能力已就绪。

Codex 频道的「原生对话」与「动态」页共用原生输入框，切换标签保留草稿与待核对回执，不能调用旧的上下文备注接口。普通聊天原样发送，支持运行中追加、原生审批、问答和图片；发送结果未知时保留待核对状态，不自动重发。协议不兼容或线程失联时显示真实错误并禁用发送。未发送过任何消息的空白任务可能不被原生后台跨启动保留，只有明确缺失且无历史、轮次或发送回执时才提供用户主动重新创建入口；已有内容的任务不得自动更换原生 ID。

0.4.3 已用安装版原生二进制、隔离数据目录和本地模型夹具验证双客户端创建、同轮追加、外部消息回流、原生后台重启后的冷恢复。实际安装版 Codex App 还需在本次修改完成后重新打开一次，才能验收真实界面和工具链；不得把隔离测试表述成该最终验收已完成。

Morrow 负责项目目录、持续职责调度、可信结果与统一看板。Codex 持续职责复用已关联的原生任务，等待空闲并检查 App 当前权限是否符合频道保存的自动执行范围；普通聊天继承 App 原生设置。调整频道配置不能悄悄分叉或清空已关联会话。其他引擎继续使用原生 CLI，保留其已实现的权限限制和精确会话交接；这些 CLI 的人类备注仅供下一轮读取，不伪装为运行中实时聊天。

运行是否成功与看板报告是否能解析是两个独立状态。原生回复和 CLI 输出完整保留，没有有效报告时不编造工作项，也不把成功执行改判为失败。普通聊天与 App 外部轮次不自动更新看板、不计入 Morrow 调度预算。自动执行遵守权限检查、次数上限、暂停与项目串行机制。CLI 子进程的超时、输出限制和进程组终止只适用于该适配器；共享的 Codex App 轮次使用原生执行状态和精确轮次停止请求，Morrow 重启不终止 App 的工作。

## 持久化与追溯

Morrow 发起或管理的项目、频道、功能、设置修改、调度动作、消息、运行元信息、输入、输出、报告和错误全部在 SQLite 中留存。看板状态变化保留前后值与操作者。已关联 Codex App 任务的外部消息、轮次、工具活动、原生请求和图片也同步记录，保留线程、轮次、消息及请求 ID，支持历史分页、增量去重和重连补齐；不导入未关联任务的私有历史。其他 CLI 在外部终端继续的完整活动仍由该 CLI 保存，Morrow 仅记录交接和会话关联。只有标签页、面板宽度等展示偏好可以保存在 renderer localStorage。

已有项目和证据必须保留。模型生成的已验证/已解决结论需要真实证据；跨项目更新、过期结果覆盖人工修改和错误的成功提示应被拒绝并留下可追溯原因。

0.6.0 原生自动工作权限：新项目与新频道默认在自己的工作区修改和验证，已有频道的权限与暂停状态保留。调度轮次使用 Codex 原生 `auto_review` 审查工具请求，并应用频道保存的只读/工作区范围；选择原生范围时沿用原生沙箱。普通对话不额外覆盖设置，已确认的原生轮次设置按 Codex 协议也会延续到后续轮次。Morrow 不自动批准原生请求，也不绕过原生审查拒绝；上线另由人确认封存版本。旧 owner/follower 连接仍可聊天，但自动工作需共享后台支持。

0.6.0 验收补充：发布等待不受旧报告 `needsHuman` 字段误暂停影响。默认反馈监测在条件满足或复查期限到达后仍持续收集字段变化，直到明确取消或频道暂停；一次性实验显式选择 `continuous:false`。多个本机工具后台同时存在时，依据已绑定任务的实际加载归属选择原后台，并保存连接归属；重连使用独立的增量序号周期，补齐原生任务历史，不新建或分叉任务。

0.9.3 续验收修正：未知复核重试接续仍有效、未被新请求替代的完成意图，原拒绝记录继续保留；并发修改不覆盖。重试附带有界的前次真实工具观察，避免丢失已完成的检查；本轮仍须独立检查并产生完整结论，不继承前次成功计数或结论。相同材料重试次数与单次复核时限保持不变。

### 旧 App 写入锁的接续

实际安装验收发现，App 可在轮次空闲时仍持有原任务写入锁。新策略不释放其他进程的锁、不操作 App、不重启 Codex：仅对升级前的旧绑定，在 CLI 明确返回 `already has an active writer` 时，通过原生 `thread/fork` 做一次接续。SQLite 保存旧任务 ID、接续回执与新旧绑定关系，界面明确显示接续说明；旧运行、证据和预算不改写，继承的轮次不重复计数。后续持续复用新 CLI 任务。普通网络失败、已归属 CLI 的任务或未确认发送不能触发该迁移；接续结果未知时不重发创建。
