## 第一阶段的行为

1. **在新的正常编排开始时保存意图。** 保存当时是否开启自动工作、任务绑定、项目说明/方向版本，以及持久化的用户意图代次。人工暂停、手动运行或继续、重新绑定、说明/方向/权限修改都会使已有自动接续候选失效；普通自动状态写入不冒充人工操作。不能用仅在内存中的 activationVersions 证明重启前无人暂停。
2. **中断即时终结。** 仍保存原 interrupted 状态、原 I/O 和权限边界，立即使旧 grant 无法再执行工作操作。另存待观察记录，明确暂停原因是原生中断还是人工暂停。旧数据缺少该意图快照时保持原状态，不能批量恢复历史暂停。
3. **只从完整原生记录识别候选。** 必须同项目、频道和当前绑定任务；有明确 `resume_interrupted_task` 标记；按任务内轮次顺序只有一个可匹配的前序编排中断，没有中间的其他工作、人工发送或指导。当前没有父 ID，因此关系标记为 `inferred-sequence`，同时保存原/续跑 run ID、nativeTurnId、标记、依据和排除理由。不能仅凭时间相近匹配；前序分页不完整、顺序冲突或多个候选时保持未确认。未来若实测出现明确父 ID，可另行增加经过验证的读取规则，本阶段不猜字段含义。
4. **App 续跑期间只观察。** 保留 native-app 来源和自己的终态；不将它重写成原 scheduled run，不注入新消息，不重发或中断原生任务。它的报告和 morrow-next 保存为原生历史，第一阶段不直接用于修改事项、关闭事项或安排调度。旧工具调用的 409 拒绝仍有意义；不提供新地址给正在续跑的任务，也不把旧 request-id 重试执行到新 run。
5. **结束后有条件恢复正常调度。** 只有候选 completed、原自动工作已开启且用户意图代次未变，绑定/目标/权限检查仍有效、没有待答问题或后来的指导时，才把原生中断导致的暂停转为正常等待。保存“App 续跑完成，下一轮核对其工作”的原因；普通调度器决定何时运行，不直接调用发送。预算、项目串行、复核、工作树及升级排空门禁全部照常生效。新轮次获得自己的新 grant，并核对原生历史、实际文件和既有事项后决定下一步，不能继承一条未经核验的通过结论。
6. **条件不足则保留暂停。** 失败、再次中断、明确人工暂停、关联歧义、缺少完整原生状态或意图变更都不恢复。首版只处理单次中断与单次续跑，不猜测多段链。缺失权限字段不解释为“未变化”；只有正常接入路径能确认适用权限时才可调度。重启后先重读原生状态，观察历史本身不会触发新任务。

第一阶段的取舍：App 续跑仍可在自己的原生权限范围内执行，但其 Morrow 工具调用可能因旧 grant 结束而被拒绝，相关看板和安排由后续正式轮次核对。这样能处理自动工作意外停住的问题，却不宣称实现了轮次内无缝授权交接。若真实使用表明这仍不足以完成工作，再单独提出显式新授权交接方案。

## 实际行为（第一阶段已实现）

代码位置：新增 `service/app-resume.ts`（`AppResumeTracker`，挂在 `engine.appResume`）；`service/protocol.ts` 增加 `WorkIntent`、`IntentAction`、`ChannelIntent`、`AppResumeRecord`、`AppResumeSummary` 与纯函数 `appResumeSummary`；`service/store.ts` 增量迁移 `app-resume-v1` 建 `channel_intents`、`app_resumes` 两张表（外加 `app_resumes_channel`、`app_resumes_thread`、`runs_native_turn` 索引），并把一行摘要放进轮询快照的频道投影；`service/engine.ts` 在 `performAction` 推进代次、在 `finishFailure` 记录待观察；`service/native-conversations.ts` 在 `startScheduled` 保存意图快照、在 `bind` 与人工 `chat` 发送处推进代次、在 `ingest` 末尾做只读识别；`service/server.ts` 在项目目标/说明与频道方向/权限的修改入口推进代次。

- **意图快照**：每次正常编排轮次在 run 行上保存 `workIntent`：自动工作是否开启、绑定任务、项目说明版本、工作方向、权限，以及频道的持久「用户意图代次」。代次存在 `channel_intents`，重启后仍在。
- **人工意图失效**：暂停、运行一次、继续、重新绑定、项目目标/说明修改、频道方向或权限修改、人工发送或收到指导都推进代次，并把仍在观察的候选记为 `kept-paused`。人工暂停另外记 `pausedAt`。
- **中断即时终结**：原 run 保持 `interrupted`、`reportStatus` 与旧凭证拒绝不变；另存 `app_resumes` 记录，`pauseCause` 区分 `native-interrupt` 与 `human-pause`。缺 `workIntent` 的历史轮次不产生记录。
- **只读候选识别**：同项目、频道、当前绑定任务；`turnTrigger === 'resume_interrupted_task'`；历史完整；原轮次与候选在任务内紧邻（中间没有任何其他轮次）；候选投影的 run 来源必须是 `native-app`。关系记 `inferred-sequence`，保存原/续跑 run ID 与 nativeTurnId、标记、`basis` 与 `exclusions`（只追加，不重写）。
- **有条件恢复**：候选 completed、原自动工作开启、代次未变、绑定/方向/说明版本/权限一致、无待答问题、续跑轮次内与其后都没有人工消息（含轮次内的 steering）、没有待答原生提问，且频道仍是那次暂停留下的 `paused` 状态时，在一个事务内重读代次与频道状态，把暂停转为 `waiting` + `nextRunAt`（+5 秒）并重新开启自动工作，写 `appliedAt` 与「App 续跑完成，下一轮核对其工作」的审计行。不发送、不重发、不中断；下一轮由调度器启动并领取新凭证。
- **保留暂停**：任一条件不成立即 `kept-paused` 并记原因；续跑 failed/interrupted、多个标记候选、中间有别的轮次、候选被别的记录占用、候选不属于 App 自己都不恢复。
- **界面**：频道页多一条可折叠的「App 续跑：…」行（当前状态 + 一句原因），详细 ID 留在工作日志的审计记录里；不加聊天区。

## 实际行为与本方案的差异

1. **未确认是否可再评估**：方案只说「保持未确认」。实现把排除原因分成两类：任务内顺序已经确定的歧义（多个候选、中间有别的轮次、候选被占用、候选非 App 自有）是终局，此后不再重新匹配；而「历史分页不完整」「候选 run 尚未投影」这类暂时读不到的情况会记为 `unconfirmed` 并在下一份完整快照里重读。理由是重连时先到的往往是局部历史，若一律终局化会让功能在真实使用中永远不触发；而真正的歧义只会随轮次增加而更明确，终局化更安全。
2. **紧邻要求写死为「下一轮」**：方案说「中间没有别的工作、人工发送或指导」。实现直接要求候选是原轮次在任务内的**下一轮**；只要中间有任何一条轮次就记 `intervening-turns` 并终局。比逐类判别更保守，也更容易核对。
3. **多了一条「待答原生提问」检查，并把「后来的指导」扩到续跑轮次之内**：除方案写的待答问题（`work.awaitingReply`）与后来的指导外，实现还要求该任务没有 `userInput`/`mcp` 类的待处理原生请求；「后来的指导」从中断那一轮之后算起，包含人在 App 续跑轮次里插入的 steering 消息，不只是续跑结束之后的轮次。方向与方案一致（更保守），但方案未写。
4. **暂停原因来自持久记录而非调用路径**：`pauseCause` 由 `channel_intents.pausedAt` 与代次判定，不依赖是哪个调用终结了这一轮，因此重启后重放同一终态仍得到同一原因。
5. **CLI 夹具路径不写意图快照**：`workIntent` 只在原生编排入口 `startScheduled` 写。`MORROW_TEST_MODE` 的 CLI 子进程路径不写，因此它的中断也不会产生接续记录；真实 Codex 频道一律走原生路径。
6. **人工聊天发送会推进两次代次**：一次在提交时，一次在 `acceptNativeGuidance` 处理回执时。代次只用于比较是否相同，重复推进不影响判定，故未额外去重。
7. **界面只在频道页加一行**：方案说「用户只看到当前状态和可展开的关联原因」。实现把这行放在频道页，工作日志里则是三条审计事件（已记录待观察／已推断关联／已恢复等待）各一次，不重复。

## 已验证与未验证

- 已在隔离环境用真实形状重放验证：正确候选只恢复普通等待且下一轮用新凭证；无标记／别的任务／前序非编排轮次／历史不全／多个候选不关联；人工暂停在中断前、候选后、终态处理前后都优先且不重复发送；重启后重放不改判；新指导／重新绑定／方向、说明、权限修改／自动关闭／手动单次运行使候选失效；续跑 failed/interrupted 与多段续跑不恢复；重复、乱序与重连补历史至多恢复一次；旧凭证与旧 request-id 始终 409；预算、复核、升级排空、工作树门禁照常拦住恢复后的等待。夹具见 `tests/fixtures/app-resume-live01.json`，用例见 `tests/app-resume.test.ts` 与 `desktop/renderer/features/ChannelAppResume.test.tsx`。
- 仍未验证：真机上 App 是否总在这些条件下写这个标记、恢复后的首轮实际耗时与收益、以及本次改动在安装版中的行为。收益保留未知；真机观察仍按下文「真机观察」一段的约束进行。

## 持久化与并发约束

- 用增量、幂等迁移增加接续记录和用户意图代次；以绑定任务及原/续跑 nativeTurnId 去重。状态与“恢复正常等待”的写入在同一事务内校验代次并应用，重复终态或重启重放只能应用一次。
- 原 run、原报告、错误和凭证记录不覆盖；候选关系变化追加原因。首版不调整已完成/未知复核、原 execution 绑定或历史证据来源。
- 新人工操作使候选失效，之后重放旧 completed 也不能覆盖新暂停。若恢复等待与人工暂停竞争，事务先后均须得到人工暂停优先的结果；新运行仍有现有启动代次检查。
- 沿用原生真实 busy 状态阻止并行调度；续跑引起的文件变化需重新只读观察。不能为接续自行清理工作树或改写 #26 的事项归属判定；不确定的归属进入现有门禁/人工处理。#26 报告入口漏洞修复前仍不能发布此候选。
- 用户只看到当前状态和可展开的关联原因，详细 IDs 留在详情。不增加重复聊天区或要求维护新的工作清单。

## 实施范围与验收

批准后按两个小步实施：先做持久记录、人工意图失效和只读候选识别；检查通过提交后，再接入有条件的调度恢复与现有工作日志提示。预计涉及 `service/native-conversations.ts`、`service/engine.ts`、持久化类型/迁移及人工修改入口；不改 `service/codex-*.ts` 的原生协议、App 设置、授权校验和人侧 acceptance/live 实现。若发现必须变更协议或轮次内授权，再提出具体差异。

使用 `tests/harness` 与已保存事件结构做有界重放，不创建真实 App 任务。关键反例如下：

| 场景                                                                  | 必须得到的结果                                                                  |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 单一明确标记、唯一前序、原自动开启、续跑完成                          | 独立保留两条 run，候选标为推断；仅恢复普通等待，下一正常轮次用新凭证            |
| 时间相近但无标记、别的任务/频道、前序不是编排轮次、历史不全、多个候选 | 不关联或记录未确认；不恢复                                                      |
| 人工暂停发生在中断前、候选后、终态处理前后；重启后重放                | 人工暂停始终有效，不重复发送                                                    |
| 有新指导、重新绑定、权限变更或无法核验、原自动关闭、手动单次运行      | 原候选失效，不能开启自动工作                                                    |
| 续跑 failed/interrupted 或出现连续多段续跑                            | 保留失败与观察，首版不自动恢复                                                  |
| 重复、乱序、重连补历史、终态重复处理                                  | 至多一次恢复；不从缺少意图快照的旧历史自动启动                                  |
| 原凭证、新旧 request-id、过期准备记录、跨归属报告                     | 旧 run 的新调用始终拒绝；不重放旧副作用、不迁移原执行证据、不以报告绕过事项归属 |
| 预算不足、复核进行中、升级排空、其他频道未提交改动                    | 继续由现有门禁等待/拒绝，不能因为接续而跳过                                     |

收益尚未验证。机制验收分别记录：正确候选后能否恢复普通调度、是否重复发起、人工暂停是否被覆盖、旧 grant 是否接受了新调用。后两项以及重复发起必须为零。受控重放通过后仍需完整检查、独立发布级复核及人工发布批准。

真机观察只在经批准安装后、已有任务自然发生这类事件时开展，用 evidence.link 保存实际工具记录；不为了试验去改 App 模型/权限设置、强制中断任务或运行人侧 live harness。记录原生事件时间、服务观察时间和后续正式轮次的首次开始，分别报告恢复结果与等待耗时。没有自然样本时保留效果未知；不得用模拟回执填补。
